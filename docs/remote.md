# Remote control from a phone

`hivegrid-remote` is a small web server that shows every Hivegrid agent on your phone and lets you answer them: follow an agent's chat live (built from its omp session file) or the tail of its screen, send a prompt, press a key (`Enter`, `Esc`, arrows, `y`, `n`, `1`..`9`), answer a plan review, acknowledge a finished agent, change its model and thinking level, see when an agent stopped on its account's usage limit, move its chat to another account, start a new omp session on one of your accounts (in any folder below your home directory, found with a search box), quit a session with a swipe, start a past one again from a history page, see the files and images an agent sent with `hivegrid-send`, and see a prompt you sent while the agent works greyed out in the chat until omp takes it. It also reports each account's quota and token usage and the machine's CPU, memory, disk and GPU. It is made for reaching your agents over [Tailscale](https://tailscale.com); it listens on the local machine only and is published to your tailnet by `tailscale serve`. Python standard library only; the web page is a single page served by the same program, with no build step and no remote assets.

It lists agents and, only when you switch the terminal on (see Terminal), gives the phone a shell of its own. Without that it types only into agents (a prompt, keys, an answer) and, for an account switch, one `cd … && omp …` line into the plain shell that is left after omp quit (see Switching account; the line is appended to whatever was already typed at that prompt). It cannot close panes (a quit leaves the shell for you to close), jump the window's focus or read arbitrary files: the only files it reads for the phone are an agent's own omp session file (see below), the files `hivegrid-send` put in the outbox (see Files and images to the phone), the quota cache numbers, the monitor log and the terminal's font. The one pane it can open is a new omp session from `POST /api/sessions`, on an account you offered it and in a folder below your home directory (see Sessions started from the phone); it also names folders (never their contents) to the search box.

## Set up

1. **Create the token.** It is a 256-bit random secret, kept in `~/.config/hivegrid/remote-token` (mode `0600`; next to `settings.json`, so `HIVEGRID_SETTINGS` moves it too):

   ```sh
   hivegrid-remote token            # creates it and prints it; with a file already there it prints the path
   hivegrid-remote token --show     # prints it again
   hivegrid-remote token --rotate   # replaces it; the running server accepts only the new one at once
   ```

2. **Start the server** (from a shell on the machine that runs Hivegrid):

   ```sh
   hivegrid-remote serve            # http://127.0.0.1:8787/
   ```

   It exits with status 1 when the token file is missing or unsafe (run `hivegrid-remote token` first), never creates a token itself and never prints it. It finds the Hivegrid window's socket by itself, so it also works from a service that was not started inside Hivegrid, starts without a window (the API answers `503 no_mux` until one exists) and follows a Hivegrid restart without a restart of its own. When a stock WezTerm runs besides Hivegrid, pass the Hivegrid window's socket with `--socket` (and `--wezterm` for its `wezterm` binary) so the server does not pick the wrong one.

3. **Publish it to your tailnet** (HTTPS needs MagicDNS and HTTPS certificates enabled in the Tailscale admin console):

   ```sh
   tailscale serve --bg --https=443 http://127.0.0.1:8787
   tailscale serve status
   tailscale serve --https=443 off      # remove it again
   ```

   The `tailscale serve` flags differ between Tailscale versions: check `tailscale serve --help` on your machine before you run the line above. Never use `tailscale funnel`: it publishes the page to the whole internet.

4. **Open it on the phone** (the phone is signed in to the same tailnet), once, with the token in the URL fragment:

   ```text
   https://<machine>.<tailnet>.ts.net/#t=<token>
   ```

   The page stores the token in the phone's `localStorage` and removes it from the address. A fragment is never sent to a server, so the token is in no log. "Add to Home Screen" makes a shortcut that opens the page full screen with the Hivegrid icon (`/icon.png`, `/logo.svg`). After a rotation (or a 401) the page shows a token field again.

An alternative without `tailscale serve` is `hivegrid-remote serve --bind $(tailscale ip -4)`: plain HTTP inside the WireGuard tunnel. It works, but the browser calls it an insecure context and the server needs tailscaled up first. The bound address is allowed as a `Host` automatically, so the phone URL may use that IP or the machine's MagicDNS name; any other name needs `--allow-host`.

**Tailscale ACL.** A tailnet with a custom policy can drop the phone's traffic even though ping works (`tailscale ping` is ICMP; the page is TCP 443). If the phone is a tagged device, or your policy has no rule from it to this machine, add a grant that allows only this machine's HTTPS port, for example:

```json
"hosts":  { "my-workstation": "100.x.y.z" },
"grants": [ { "src": ["tag:trusted"], "dst": ["my-workstation"], "ip": ["tcp:443"] } ]
```

(`src` is your phone's tag or user; `100.x.y.z` is `tailscale ip -4` on the workstation.) This is the only network barrier besides the token, so keep it narrow.

## Run it as a user service

`hivegrid-autostart install` writes, enables and starts the systemd user unit for the server (and one for the Hivegrid window); [docs/autostart.md](autostart.md) describes the unit, why it restarts the way it does and how to undo it, and is the only place that lists it. Run `hivegrid-remote token` once first: without a token file the server exits with status 1, and systemd does not restart it for that (or for bad arguments). Then:

```sh
hivegrid-autostart install
journalctl --user -u hivegrid-remote -f
```

To run the server with the phone terminal, switch it on in `settings.json` (`remote.terminal`, see Terminal) instead of editing the unit: a later `hivegrid-autostart install` rewrites `ExecStart`.

## If the page does not work

| Symptom | Cause and fix |
| --- | --- |
| The phone times out, while `curl https://<machine>.<tailnet>.ts.net/healthz` on the workstation prints `ok` | The Tailscale ACL blocks TCP 443 from the phone (see above), or the phone cannot resolve the name (Android Private DNS). |
| `502` from the tailnet URL | `hivegrid-remote` is not running: `systemctl --user status hivegrid-remote`. |
| The page loads but says "no Hivegrid window" (`503 no_mux`) | No Hivegrid window is open, a stock WezTerm was picked instead (pass `--socket`), or the unit has `PrivateTmp` (remove it). |
| The token field appears again | The token was rotated or the site data cleared: open the `#t=` link once more (`hivegrid-remote token --show`). |

## Read-only mode

`hivegrid-remote serve --read-only` (or `HIVEGRID_REMOTE_READ_ONLY=1`) removes every write: all `POST` requests answer `403 readonly`, the page hides its controls and shows an amber `read-only` chip. Agents, states and tails stay visible. Use it for a phone you only want to watch with.

## Terminal

The page can open a real login shell on this machine: a pty running your `$SHELL -l` (else the account's shell, else `/bin/sh`) as your user, in `$HOME`, with `TERM=xterm-256color`. It is not a pane of the Hivegrid window: the window and the dock never see it, and nothing goes through `wezterm cli`. **It is off by default and it is the most dangerous thing this server can do: a stolen token becomes a shell as your user** (your files, SSH keys, cloud credentials, everything an agent can reach and more). Switch it on only if you accept that, and keep the Tailscale ACL narrow: allow port 443 of this machine to your own phone's user or tag only (see *Tailscale ACL* in Set up).

**Switching it on.** Either put this in `~/.config/hivegrid/settings.json` (literally `true`; any other value means off):

```json
{ "remote": { "terminal": true } }
```

or start the server with `hivegrid-remote serve --terminal` (`HIVEGRID_REMOTE_TERMINAL=1`; from a shell or a checkout, not in the user service, whose unit `hivegrid-autostart install` rewrites: use the `settings.json` key there). The file is read at every request, so no restart is needed to switch it on, and **deleting the key (or setting it to anything but `true`) ends every open shell at the next terminal request or within 5 seconds**. `--terminal` is the stronger switch: the file cannot turn it off, only a restart without the flag does. `--read-only` always wins: with it the terminal is off whatever else is set, every `/api/terminals` request answers `403 readonly`, and `--terminal` is ignored (a note says so at start). While it is off the answer is `403 terminal_disabled`, and `/api/meta` says `terminal: false`, so the page shows no Terminal button.

**Using it.** With the terminal on, `/api/meta` says `terminal: true` (and lists the `terminal` capability) and the page's top bar shows a `>_` button that opens `#/term`. The first visit opens a shell sized to the screen; the page remembers which one it showed, so reloading the page or coming back after the phone slept reattaches to the same shell with its screen and running programs. `+` opens another (up to 4), `A−` / `A+` change the text size (remembered), `✕` ends the shell you are looking at, and a chip shows whether the connection is live, retrying or offline. Tapping the screen brings up the phone keyboard; the row of extra keys under the screen has `Esc`, `Tab`, sticky `Ctrl` and `Alt` (they apply to the next key, from either keyboard), the arrows (hold to repeat), `Home`, `End`, `PgUp`, `PgDn`, `^C`, `^D`, `^Z`, `|`, `~`, `/`, `-` and `paste`. A hardware keyboard works too, including `Ctrl`, `Alt`, function keys and bracketed paste. Text is selected and copied with the browser's own selection. The transport is plain HTTPS requests (a held `GET` for output, small `POST`s for keys), no WebSocket, so whatever forwards the page, `tailscale serve` included, forwards the terminal.

**What survives.** A shell lives on the server, not in the page. A dropped connection, a reload or a locked phone leaves it running; the page asks again for the output from where it stopped (the server keeps the last 256 KiB), and a key request whose answer got lost is recognised by its number and not typed twice. A shell nobody looks at for **15 minutes** (`remote.terminal_detached_minutes`) is closed, and one that got no keystroke for **60 minutes** (`remote.terminal_idle_minutes`), even while the page is open, is closed too; both settings take whole minutes from 1 to 1440 and are read at every request. A shell also ends when you type `exit`, when its token is rotated (`hivegrid-remote token --rotate` ends the shells opened with the old token at once), when the server stops, and when the terminal is switched off. Each shell belongs to the token that opened it; another token cannot see or reach it.

**What the emulator supports.** The page draws the terminal itself (`/term.js`, no library, no external asset) as an xterm-like emulator: cursor addressing, scroll regions, insert and delete of lines and characters, erase, tabs, 16, 256 and 24-bit colours with bold, dim, italic, underline, strikethrough and inverse, the alternate screen, application cursor keys, bracketed paste, DEC line drawing, the window title (shown above the screen, control characters removed), wide and combining characters, 2000 lines of scrollback, and the replies programs ask for (device attributes, cursor position, screen size). That covers a login shell, coloured `ls` and `git` output, `less`, `man` and `top`; full-screen editors such as `nano` and `vim` draw and take keys (use the extra-key row for `Esc` and `Ctrl`). Partial or missing: **no mouse reporting** (programs that ask for the mouse get none, so tapping does nothing inside `vim`, `htop` or `tmux` mouse mode), no images (sixel, kitty), no hyperlinks (OSC 8) or clipboard writes (OSC 52), no cursor shape or blink, no ligatures, no right-to-left shaping, character widths from a built-in table that can differ from your font for rare symbols, and no function keys on the extra-key row (a hardware keyboard has them). The font is the machine's mono font (see the static routes) or the phone's monospace. A very fast output stream (`cat` of a large file) is drawn in batches, so the screen can lag behind the shell, and only the last 256 KiB is replayed after a reconnect.

**Turning it off again.** Delete the `remote.terminal` key, restart without `--terminal`, or run with `--read-only`; `hivegrid-remote token --rotate` ends every shell and locks the phone out in one step. Limits are in *Limits*, the threat in *Threat model*.

**What the user service does to these shells.** Under `hivegrid-autostart install` the shells inherit the unit's hardening (`NoNewPrivileges`, `UMask=0077`, `RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6`): `sudo` and `su` fail inside a phone shell, files it creates are mode `0600` (not `0644`), and tools that talk netlink (`ip`, `ss`) fail. A server started by hand has none of that. A process started with `nohup` or `setsid` survives closing the terminal and a token rotation: `hivegrid-remote token --rotate` ends the shells, not the children they detached.

## Usage limit

When an agent's account hits its usage limit (the 5-hour or the weekly window), omp's turn ends on a refused request and the agent would look `done`. Hivegrid reads that as its own state, `limit` (glyph `⊘`, red, listed right after `needs you`; the same word and glyph in the dock, hive, picker and header, see [docs/features.md](features.md)), and the page shows it on the agent's row (`⊘ limit · 5-hour limit · resets in 2h05m`), in its chat (a red `usage limit reached` line where the turn ended and a card above the composer with the reset time and a **Switch account…** button), in the filter chips and in the list footer; the page title counts it with the agents that need you.

**How a limit is recognised, and how sure that is.** The signal is a message in the session file, not a screen scrape: the last message of the chat is an assistant message with `stopReason: "error"`, `errorStatus: 429` and an error text that names `rate_limit_error` (or a usage or quota limit), usually followed by `retry-after-ms=<n>`. That is what omp 18 writes in the real sessions this was built from (the retry time was always hours: 20 minutes to 90 hours). `retry-after-ms` is the time until the account's window reopens, so `reset_at` is the end of the refused request plus it. The retry-after may be missing, and then a 429 with `rate_limit_error` is still a limit, with an unknown reset (`reset_at: null`; a number of more than 12 digits or beyond 400 days reads the same). That is also the heuristic's false-positive risk: a provider's plain rate limit without a retry-after looks exactly like the account's window. Only the last message counts (a chat that went on after the refusal is not limited), and a refusal that reopens within a minute is a short burst limit omp retries by itself, not a limit. This is a heuristic on omp's error text, not an API: another provider's error, or a changed wording, reads as `done`. The extension `ext/hivegrid-agent-state.ts` decides it when the loop ends and writes `state: "limit"` with `limit: {hit_at, reset_at}` into the agent's state file; for an omp whose extension predates that, the server looks at the end of the session file of a `done` agent itself (the last 256 KiB, remembered while the file does not change), so the page shows the limit either way. A new turn clears the state. A limit does not expire by itself (omp does not know when the account is usable again): once its `reset_at` has passed, **Acknowledge** (Actions sheet, `POST /api/agents/{id}/ack`; `a` in the hive) makes it `idle` until it hits again, in the dock, the hive, the picker, the header count and Alt+n alike; a limit with an unknown or future reset cannot be acknowledged. A resumed chat whose last message is an old refusal stays `idle` until it is prompted.

**Which window.** `limit.window` is `five_hour` or `seven_day` when it is known: the window of the agent's account whose own reset time (from the claude-quota cache) is the refusal's reset time, or `seven_day` when the reset is more than five hours away. Otherwise it is `null` and the page says `usage limit`: a 5-hour limit and a weekly limit that ends soon look the same, and a guess would be wrong half of the time. `reset_at` and `hit_at` are epoch seconds or `null`; `label` is the words the page shows and `account` the label of the account the agent runs on (`null` without a paired account). The agent can be prompted in this state; it fails again until the account is switched or the limit reopens.

## Switching account

A chat moves to another account the way the header's account pills do (see [docs/accounts-and-quota.md](accounts-and-quota.md)), with `bin/omp-switch`; nothing of that is implemented again. The page offers it on a limited agent's card and in **Actions › Switch account**, and asks for a confirmation that names the account. `GET /api/agents/{id}/accounts` lists the accounts the chat can move to: those paired with an omp profile in the settings (an account without one cannot take a chat), not the one it runs on, not hidden ones; `POST /api/agents/{id}/account` takes the `profile` of one of them (`400` for anything else) with `"confirm": true`.

**When.** Only while the agent is `limit`, `done` or `idle` (`409 agent_not_ready` while it works, is busy, waits for an answer or has exited: the phone never interrupts a turn for a switch, and there is no "switch anyway?" dialog as on the desktop), runs under an omp profile (an agent on omp's default configuration has no profile to move from) and has published its process id. `--read-only` refuses with `403`. The phone can neither pick a path nor a command: the only inputs are the agent and a profile name from the offered list. The move is typed into a plain shell: after omp quit, the line below is typed where the shell prompt is, appended to any text already typed at that prompt.

**What happens.** The same move as in [docs/accounts-and-quota.md](accounts-and-quota.md), which counts four steps (its step 2 includes the wait of step 3 here). The call answers `202` once the first two steps are done, then a worker finishes the move:

1. `omp-switch locate` finds the chat's session file (read-only; nothing has changed yet, and a failure answers `409` with omp still running);
2. Ctrl+D is sent to the agent's pane, only when the agent's process is still alive and omp is still the program in front in that pane (otherwise `409 agent_not_ready` and nothing is sent: Ctrl+D would close a shell): omp quits on an empty prompt, and with unsent text in its prompt it stays;
3. the worker waits up to 5 seconds for omp to exit and for the pane to show a shell (it never kills anything: omp that stays means the switch is abandoned and the page says so; a pane that shows anything but a shell afterwards is left alone too);
4. `omp-switch transfer` copies the session file, its artifact directory and the blobs it references into the other profile under the same names, never overwriting and never touching the old profile's files;
5. `cd <directory> && omp --profile=<new> --resume <copy>` is typed into the shell, so the same chat continues with its whole history on the new account (a chat without a message yet starts a fresh `omp --profile=<new>`). When the transfer fails, the chat is resumed on the old profile instead, so the pane is never left at a bare shell.

The paths in that line come from `omp-switch`, are checked to be session files below the right profile's `agent/sessions/` and are shell-quoted; control characters never get through. The new omp process is a new agent in the same pane, so its row keeps the same number.

**What the page shows.** While it runs, the agent's `switch` is `{"state": "running", "to", "message", "since"}`: the chat shows a blue card `Moving the chat to <account>` and the list row `moving to <account>`; the row reads `exited` for a moment, because omp has quit and the shell is showing. Afterwards `switch` is `done` (`the chat continues on <account>`, a green card for 2 minutes, while the new omp starts and the agent's state is its own again) or `failed` with the reason (a red card; omp kept running, or the chat went back to the old account). Nothing of this is stored: restarting the server forgets a running move's status but not its effect. A move that has begun cannot be cancelled from the phone. Not exercised against the real omp and real accounts in this repository's tests: they use a fake `omp-switch` and fake panes; `dev/check` never moves a real chat.

## Files and images to the phone

An agent (or you) runs `hivegrid-send FILE...` in a Hivegrid pane, optionally with `--note "text"`, and the files appear in that agent's chat on the phone: an image as a picture (tap to open it full size), any other file as a name and size, with a **save** button. Tell the agent once: "to show me an image or a file, run `hivegrid-send <path>`".

- **Where it is kept.** In memory, not on the disk: `$XDG_RUNTIME_DIR/hivegrid-outbox` (a tmpfs, the same place as the agents' state files), else `/tmp/hivegrid-outbox-<uid>`; `$HIVEGRID_OUTBOX` overrides it for both the sender and the server. The directory is mode `0700`, a reboot empties it. At most 20 MiB per file, 50 files and 100 MiB in all, none older than 2 days; the oldest go first on the next send. Sending copies the file, so the original may change or go away.
- **Which agent.** The pane the command runs in (`$WEZTERM_PANE`; `--pane N` names another). The window's socket name is stored too, so after a Hivegrid restart (pane numbers start again) old files do not show up on a new agent that got the same number.
- **What the phone can read.** Only what `hivegrid-send` put there: the server never opens a path the phone names, and every entry is checked again when it is read (a regular file of your user, the size the metadata says, a private directory, a clean id). The type is decided from the file's first bytes, never from its name: an SVG or HTML file is a download, never drawn or run. The page fetches the bytes with the token in a header and shows them from a `blob:` URL; the content security policy allows `blob:` images and nothing else new.
- **Read-only mode.** Files are data the server only reads, so a `--read-only` phone sees them too; sending needs no token (it is a local command run by you or your agent).

## Queued prompts

omp writes a prompt to its session file only when it accepts it, and while the agent works it queues the prompt first. So that a prompt sent from the phone does not look lost, the chat shows it at once as a greyed bubble after the last real item (dashed border, no fill, and the words `queued, waiting for the agent` with the send time: it is told apart without colour). When omp accepts the prompt and the real user message appears in the session, the greyed bubble is replaced by it in the same update. An agent that was idle accepts a prompt at once, so its bubble only shows for the moment before the file changes.

- **Where it is kept.** In the server's memory, per agent, so a reload, a second phone and the polling loop all see it; the chat answer carries it as `pending_prompts` and its revision changes with it, so a held request wakes when one is added, replaced or given up. A restart of the server forgets it. Only a prompt the agent took is recorded (`POST /api/agents/{id}/prompt` that answered `200`); a refused, failed or read-only request records nothing, and so do plan answers and text typed into a question (they are not queued prompts).
- **How it is replaced.** By a user text item of that agent's session file that was written after the send (by item number in the same file, else by time) and whose text is equal after trimming trailing blanks and blank edge lines. One item replaces one prompt, the oldest with that text, so the same prompt sent twice shows two bubbles and loses them one at a time; an older identical message in the chat is not taken for it. It is done by the server on every look, so a prompt accepted while the page was closed is gone when the page opens again. omp may change a prompt before writing it (expanding a command, for instance); such a prompt is not recognised and goes by the rules below.
- **When it is given up.** After an hour; when the agent has been `idle` or `done` for 10 seconds since the send (omp holds a prompt only while it works, so it was a command, dropped or taken back); when the pane runs another omp process; when the agent is gone. An agent that exited leaves its prompts for 10 minutes as `failed`, drawn with a red dashed border and `not delivered`. At most 20 prompts per agent and 64 agents are kept, the oldest first.
- **Safety.** The text passes the same sanitizer as the rest of the chat and the page sets it with `textContent` only; the content security policy is unchanged.

## Quitting a session

Swipe an agent's row to the left on the phone (touch or pen) and a red **Quit** button slides out; tapping it asks for a confirmation, then quits that session. **Actions › Quit session** does the same without a swipe (mouse, keyboard, screen readers; the swipe is only a shortcut). A swipe that is mostly vertical scrolls the list, a tap on an open row closes it, and the list is not rebuilt under a finger.

- **What happens.** `POST /api/agents/{id}/quit` with `"confirm": true` sends Ctrl+D to the agent's pane, only while the agent's process is alive and omp is the program in front in that pane (otherwise `409 agent_not_ready` and nothing is sent: Ctrl+D would close a shell). omp quits on an empty prompt and stays when it holds unsent text; the call waits up to 5 seconds for the process to go and 3 more for the pane to show a shell, and answers `409 agent_not_ready` with "the session keeps running" when omp stayed. It never kills a process and never closes a pane: the shell that is left is the desktop's to close.
- **Gone from the list.** An agent whose omp has exited (quit from the phone, from the desktop, or crashed) is no longer listed on the phone, in the filter chips, the counts or the page title; its row used to stay as `exited`. Only a chat that is being moved to another account stays for the moment omp is gone (see Switching account). The desktop's dock and window are not touched.
- **When.** Only while the agent is `idle`, `done` or `limit` and is an omp agent with a known process id (`can.quit` says so; `409` while it works, is busy or waits for an answer: the phone never interrupts a turn to quit; use **Interrupt** first). A quit of an agent whose account switch is running is `409 conflict`; a pane is quit one at a time. `--read-only` refuses with `403`. Rate limit: 4 at once, then one every 2 seconds (`429`).
- **Undo.** The session file stays: **History** lists it and **Revive** starts it again.

## History

The menu's **History** page lists the past omp sessions of the machine, newest first: the session's title (else its first message), that message, its directory, its account and how long ago it was last used, 30 at a time (**older sessions** loads the next page). A session an agent has open right now is marked `open in agent N`. **Revive** (after a confirmation) starts it again with `omp [--profile=<account's profile>] --resume <file>` in a new pane in the session's own directory and, like every pane the phone starts, asks the window to arrange the grid (see Sessions started from the phone).

- **What is listed.** The top-level session files of `~/.omp/agent/sessions` and `~/.omp/profiles/*/agent/sessions` (a subagent's transcript is no session of its own), of your user, at most the newest 20000. A session nobody ever wrote a message in is left out. Nothing is stored for this: the server reads the files, caches the walk for 3 seconds and reads at most 64 KiB of each file shown.
- **What the phone can ask for.** Only an opaque id from the listing (a digest of the real path). The server walks the same directories again to find the file, checks it again as it does for the chat (a regular `.jsonl` of your user below `~/.omp`, no symlink out), takes the profile from the file's own directory and shell-quotes the path. The phone can neither name a path nor a command. A session whose directory is gone, whose path cannot be typed safely (a backslash or control character) or that is open in an agent is not revivable and the listing says why; `409`/`404` if that changed since. Needs the plain `omp` command (`HIVEGRID_AGENT_CMD` unset), like a profile does.
- **Limits.** Revives share the new-session limit (3 at once, then one every 5 seconds) and the same session is not revived twice within 10 seconds (`409 conflict`). `--read-only` lists but cannot revive.

## Sessions started from the phone

**Where.** The new-session page offers `~`, the directories of live agents and the folders of `~/Projects`, and a search box for any other folder: type words (`billing api`) to look for folders whose name or path contains all of them, or a path (`~/work/cl`) to complete it. Anything the search lists can be started in. The server accepts a folder only when it exists and, with symlinks resolved, lies below your home directory (or `~/Projects` when that is a link elsewhere) with no hidden component: the phone cannot start a session in `/etc`, in `~/.ssh` or through a link that leads out of the home. The search never enters hidden folders, symlinks, `node_modules`, `venv`, `target`, `dist` or `build`.

**Layout.** Nobody is at the laptop to press the arrange key, so the new pane asks for it itself: its command first sets the user var `hivegrid_arrange_new` on its own pane (an escape sequence printed by the shell line that starts omp), and `config/layouts.lua` arranges the grid once, 0.4 seconds later, with the same arrange as `CTRL+SHIFT+a` (panes keep their reading order and numbers, every pane is moved, never recreated). The keyboard focus stays where it was. It only happens when the new pane's tab is the window's active tab, and only for panes started from the phone: the desktop's own new-agent actions never re-tile the grid. On stock WezTerm without the fork the grid is arranged the same way (it uses `wezterm cli` moves); nothing is registered when the layout module is not loaded.

## Options

## API

Every `/api/...` request needs `Authorization: Bearer <token>`; the token is accepted nowhere else (no query string, no cookie). Answers are JSON; errors are `{"ok": false, "error": "<code>", "message": "..."}`. Without a token the server serves only the page (`/`, `/app.js`, `/app.css`, `/theme.css`, `/manifest.webmanifest`), the terminal's script and styles (`/term.js`, `/term-view.js`, `/term.css`: code, no data), `/logo.svg`, `/icon.png`, the two font routes and `/healthz`.

| Request | What it does |
| --- | --- |
| `GET /api/meta` | Limits, the state vocabulary (glyph, label, colour name), the key names, whether the server is read-only, and `capabilities` (`chat`, `accounts`, `system`, `sessions`, `model`, `longpoll`: what this server version offers). |
| `GET /api/agents?wait=S` | Every agent: `id`, `label` (the dock's number, `tab·number` with several tabs), `state`, `title`, `cwd`, `since` and `age`, `reason`, a `pending` question, usage, `model` (`{id, name, provider}`), `thinking`, `context` (`{tokens, window, pct}`), `session` (a chat is available) and what can be done to it (`can`, with `model` and `account`), and for an agent stopped on a usage limit its `limit` (see Usage limit), and `switch` while or after its chat moves to another account (see Switching account). `ETag` / `If-None-Match` answer `304` while nothing changed; with `wait=S` (0 to 20 seconds) the server holds a request whose ETag still matches and answers as soon as something changed, else `304` at the timeout. The revision holds no age: the page computes ages from `since`. |
| `GET /api/agents/{id}/tail?lines=60&wait=S` | The last 5 to 400 lines of the agent's screen and scrollback, without escape sequences; `ETag` and `wait` as above. |
| `GET /api/agents/{id}/chat?limit=60&before=N&rev=R&wait=S` | The chat of the agent, parsed from its omp session file: the last `limit` (1 to 200) items whole, each `{n, ts, role (user, assistant, tool, note), kind (text, thinking, tool, image, note), text, tool}` with `tool` = `{name, summary, status (ok, error, running), output}` for a tool call and its result. `before=N` (a positive item number, `400` otherwise) returns the older items with `n < N` (`older: true`). With `rev=R` equal to the current revision the request is held up to `wait` seconds and answers `{"unchanged": true, "rev": R}` when nothing happened. `source` is `screen` (and `items` empty) when no session file is available: the page then shows the tail. A turn that ended on the account's usage limit is a `note` item of kind `limit` (`{hit_at, reset_at}`); the answer also carries the agent's `limit` and `switch`, and `pending_prompts`: `[{text, ts, failed}]`, the prompts sent from the phone that omp has not written to the session yet (see *Queued prompts*; always `[]` with `before`). The revision covers it. |
| `GET /api/agents/{id}/models` | `{current, thinking, levels, models: [{id, name, provider, reasoning}]}`: what the agent's omp can switch to (empty for an omp that was started before the extension was updated). |
| `GET /api/agents/{id}/files` | `{files: [{id, name, size, ts, image, note}]}`: the files sent from that agent's pane with `hivegrid-send`, newest first (the chat answer carries the same list as `files`, and its revision changes when one arrives). |
| `GET /api/agents/{id}/files/{file}` | The bytes of one of them. An image (a real PNG, JPEG, GIF or WebP by its first bytes) is served as its type with `Content-Disposition: inline`; everything else as `application/octet-stream`, `attachment`. `404` for another agent's file or an id that is not in the outbox. Works on a read-only server (it only reads). |
| `GET /api/accounts` | The header's accounts (hidden ones excluded) with `state` (`ok`, `expired`, `login`, `error`, `unknown`), the five-hour and seven-day quota windows (`pct`, `reset_at`) from the claude-quota cache, and the tokens and cost of the live agents running on each; plus totals. No credentials, no directories. |
| `GET /api/system` | CPU %, cores, load, memory, disk of `$HOME`, GPU (`nvidia-smi`, when there is one), uptime and up to 120 points of the last 6 hours of the monitor log (`~/.cache/hivegrid/sysstats.jsonl`). |
| `GET /api/sessions/options` | `{profiles: [{label, profile, default?, note?}], dirs: [{path, label}]}`: the accounts and the directories a new session may start in (`~`, the working directories of live agents, up to 60 subdirectories of `~/Projects`). An account without a paired omp profile can only start omp's default configuration, so all of them collapse into one entry (the `main` account when it is one of them) with `profile: null`, `default: true` and a `note` that says so. Needs no Hivegrid window. |
| `GET /api/sessions/dirs?q=…` | `{dirs: [{path, label}]}`: folders for the new-session page's search box, at most 30. A `q` that starts with `~` or `/` is a path to complete (`~/work/cl` lists the folders of `~/work` that start with `cl`, then those that contain it); anything else is words that must all appear in a folder's name or path, searched breadth-first below the home directory (6 levels, 5000 folders, 1 second; hidden folders, symlinks, `node_modules` and build folders are not entered). `q` is at most 100 characters. See *Sessions started from the phone*. |
| `POST /api/sessions` | `{"profile": "<name>" or null, "dir": "~/Projects/x"}`: starts `omp` (`omp --profile=<name>` with a profile) in a new pane of the Hivegrid window, like the hive's "new agent", and then asks the window to arrange the grid (see *Sessions started from the phone*). A `dir` is one of the options or any existing folder below your home directory (`~/…`; symlinks are resolved first, and a path that has a hidden component such as `~/.ssh` or leads out of the home is `400`); a `profile` must be one of a listed account (`400` otherwise); a profile needs the plain `omp` command (`HIVEGRID_AGENT_CMD` unset). Answers `{"ok": true, "id": N}`. Starting sessions has its own limit (3 at once, then one every 5 seconds: `429`), and the same directory and account is not started twice within 10 seconds (`409 conflict`, so a retried tap cannot start two). |
| `POST /api/agents/{id}/model` | `{"model": "provider/id"}`: switches the agent's model (a value from its `models` list; `400` otherwise). `409 agent_not_ready` while the agent is working, busy, waiting for an answer or exited, or when its omp does not publish its model. Answers `{"ok": true, "confirmed": true}` once the agent's state file shows the change (up to 3 seconds), `confirmed: false` otherwise. |
| `POST /api/agents/{id}/thinking` | `{"level": "high"}`: the same for the thinking level (one of the levels from `models`). |
| `POST /api/agents/{id}/prompt` | `{"text": "..."}`: the text and then Enter, as the hive's prompt line does. Refused while the agent waits for an answer or has exited. |
| `POST /api/agents/{id}/keys` | `{"keys": ["y", "enter"], "text": "...", "confirm": false}`: up to 8 keys, each sent on its own; a key is one of the names from `/api/meta` (`enter`, `esc`, `tab`, `shift-tab`, `backspace`, `space`, the four arrows, `ctrl-c`, `ctrl-d`) or any single `[A-Za-z0-9]` character. `ctrl-c` and `ctrl-d` need `"confirm": true`. Refused for an exited agent, so nothing reaches the shell behind it. |
| `POST /api/agents/{id}/plan` | `{"choice": "execute", "feedback": "..."}`: answers a pending plan review (`refine` needs feedback). |
| `GET /api/agents/{id}/accounts` | `{current: {label, profile}, accounts: [{label, profile, state, five_hour, seven_day}], can, why, switch}`: the account the agent runs on and the accounts its chat can move to (the ones paired with an omp profile, not the current one, not hidden ones), each with its quota windows; `can` false says in `why` what stops a switch (read-only, state, default profile, a switch already running). |
| `POST /api/agents/{id}/account` | `{"profile": "<profile>", "confirm": true}`: moves the agent's chat to the omp profile of one of the accounts from `.../accounts` (see Switching account). `400` for any other profile or a `confirm` that is not a boolean, `409 confirm_required` without `"confirm": true`, `409 agent_not_ready` in a state that cannot be switched, `409 conflict` while a switch of that agent runs, `429` at its own limit (2 at once, then one every 10 seconds). Answers `202 {"ok": true, "switching": true, "to": "<label>"}` as soon as omp was asked to quit. |
| `POST /api/agents/{id}/ack` | Acknowledges an agent that is `done` or `idle`, or whose `limit` has reached its `reset_at`; `409` for any other state (`can.ack` says which). |
| `POST /api/agents/{id}/quit` | `{"confirm": true}`: quits the agent's omp with Ctrl+D (see Quitting a session). `400` for an unknown field or a `confirm` that is not a boolean, `409 confirm_required` without `"confirm": true`, `409 agent_not_ready` (working, busy, waiting for an answer, exited, no omp in front, or omp stayed), `409 conflict` while a switch or another quit of that agent runs, `429` at its own limit (4 at once, then one every 2 seconds). Answers `{"ok": true, "quit": true}` once omp has gone. `can.quit` in the agent list says whether it is allowed. |
| `GET /api/history?limit=30&offset=0` | `{items: [{id, title, preview, dir, account, ts, live, agent, can_revive, why}], offset, limit, total, more, capped}`: the past sessions, newest first (`limit` 1 to 50). `id` is an opaque handle for the next row; `live`/`agent` say an agent has it open; `can_revive` false says in `why` what stops it. |
| `POST /api/history/{id}/revive` | `{"confirm": true}`: starts `omp [--profile=<p>] --resume <file>` in a new pane in the session's directory (see History). `404` for an id that is not (or no longer) a session of yours, `409` for a session open in an agent or whose directory is gone, `409 confirm_required` without `"confirm": true`, `409 conflict` for the same session started again within 10 seconds, `429` at the new-session limit. Answers `{"ok": true, "id": N}`. |
| `GET /api/terminals` | The terminals of this token: `{sessions: [{id, n, cols, rows, alive, exit, age, idle, in, end}], limits}`. Needs the terminal switched on (see Terminal). |
| `POST /api/terminals` | `{"cols": 80, "rows": 24}` (both optional): opens a login shell on a pty and answers the session as listed above, with `limits`. `409` at the limit, `429` when opening too fast, `502` when no shell could be started. |
| `GET /api/terminals/{id}/out?from=P&wait=S` | The shell's output from absolute byte position `P` (`wait` 0 to 20 seconds: held until there is output or the shell ends): `{from, next, end, data, reset, alive, exit, in, cols, rows}`, `data` as base64 (a character or an escape sequence can end in the next answer, so the page decodes a stream). `reset: true` says `P` is no longer in the kept output: the answer starts at the oldest kept byte and the page clears its screen first. |
| `POST /api/terminals/{id}/in` | `{"seq": N, "data": "..."}`: types `data` (any characters, at most 4096) into the shell. Requests are numbered from 0: `N` equal to the number the server expects is typed; a smaller one was applied already and is answered `{"dup": true}` without typing again (a retry after a lost answer); a larger one is `409` with `in`, the number to use. `503 terminal_busy` when the shell does not read its input. |
| `POST /api/terminals/{id}/resize` | `{"cols": C, "rows": R, "redraw": false}`: sets the pty size (the shell and its program get `SIGWINCH`); `redraw` makes a full-screen program repaint even when the size did not change. |
| `POST /api/terminals/{id}/close` | Ends the shell (`SIGHUP` to its process group, `SIGKILL` a moment later when it ignores that). |

Static routes: `/logo.svg` and `/icon.png` (the Hivegrid icon, `no-cache` with an `ETag`), and `/fonts/mono.ttf` and `/fonts/mono-bold.ttf`, the terminal's font read from the machine that runs the server (`~/.local/share/fonts/DejaVuSansMNerdFont/DejaVuSansMNerdFontMono-{Regular,Bold}.ttf`, else DejaVu Sans Mono below `/usr/share/fonts/truetype/dejavu/`; `404` when neither exists, then the page uses the phone's monospace font). The repository ships no font.

`id` is an internal handle the page never shows; people see the dock's number. Other statuses: `401` bad token, `403` wrong host or origin, or read-only, `404` not an agent, `405` a method other than `GET` and `POST`, `409` the agent's state does not allow it (or a confirmation is missing, or the same session was just started or the same chat is already moving: `conflict`), `202` a started account switch, `400`, `411` (no `Content-Length`), `413` and `415` malformed requests, `429` too many requests (`Retry-After`), `500` an internal error, `502` `wezterm cli` failed, `503 no_mux` no Hivegrid window.

**The chat.** The chat reads the agent's omp session file (`.jsonl`), found from the state file's `sessionFile`, else from the file the agent's process holds open (when it holds several: the one named after the state file's session id, then the terminal record's, then a top-level session file rather than a subagent's under the session's artifact directory, then the newest), else from omp's `terminal-sessions` record. Only a regular file of your user with the suffix `.jsonl` whose real path lies in `~/.omp/profiles/<profile>/agent/sessions/` or `~/.omp/agent/sessions/` is read; anything else (another path in the state file, a symlink that leads out, another owner) is ignored and the page falls back to the screen. The first look reads the last 4 MiB of the file, later looks only what was appended, older history is read on request (at most 32 MiB back, and never more than 5000 items per session: past that `older` is false). omp's session file is a tree (`id` and `parentId`; going back to an earlier message and continuing leaves the old path in the file): the chat shows the path that ends at the last message. A file that is rewritten (a new inode, or in place with other first or last bytes) is read afresh. A line over 16 MiB is not parsed; a `[line too large]` note stands in its place. Lines that are not JSON are skipped; text is stripped of escape and control characters and cut (12000 characters per item, 1500 for a tool output); images show as `[image]`.

**Model and thinking.** The omp extension `ext/hivegrid-agent-state.ts` publishes the model, thinking level and context fill in the agent's state file, the switchable models in `<pane>.models.json` next to it, and executes `set_model` and `set_thinking` command files like the plan-review answers. An omp process that started before the extension was updated has the old extension: it shows no model and the page hides the controls until it is restarted.

## Limits

- Request body at most 16 KiB; a prompt at most 8000 characters; at most 8 keys per request; a tail at most 400 lines (64 KiB, lines cut at 500 characters).
- Prompts, key text and feedback may contain newlines and tabs but no other control character, so no escape sequence can reach a pane.
- Writes: bursts of 10, then 2 per second; reads: bursts of 30, then 15 per second; starting a session (also a revive): 3 at once, then one every 5 seconds; quitting a session: 4 at once, then one every 2 seconds; moving a chat to another account: 2 at once, then one every 10 seconds. A held request (long poll) pays one read token when it arrives, not one per look. Five wrong tokens in a minute throttle that client for a minute, doubling while it keeps failing; a request with the valid token always passes, so a stranger's guesses cannot lock you out. A global cap on failures per minute backstops clients that cannot be told apart.
- At most 32 connections at once (more are closed at once) and 8 per client, a socket timeout of 10 seconds per connection, and 4 simultaneous `wezterm cli` calls (also `nvidia-smi`); each call gives up after 4 seconds (2 for `nvidia-smi`). A GPU answer is cached for 3 seconds, and the lookup repeats only every 60 seconds while there is no GPU (no `nvidia-smi`, or it failed).
- A long poll (`wait=` up to 20 seconds) holds one connection, looks about once a second (the chat: twice a second, a file stat) and holds no lock while it waits. Held tails of one pane share one `wezterm cli` read per second. A phone keeps about three of them (list, chat, tail), well inside the per-client cap; a held request ends at once when the server shuts down, and within a look when the client goes away (the page aborts its polls all the time), so its connection slot is free again.
- A chat answer carries at most 200 items; the parser keeps at most 5000 parsed items of each of up to 8 session files in memory (the oldest go first).
- A chat answer carries `gen`, a number that changes when the session file is parsed afresh (it was replaced or rewritten, so item numbers `n` no longer match earlier answers); the page then drops the items and nodes it holds for that chat. It is `0` when `source` is `screen`.
- The page long-polls (the list, the open chat or tail) with timeouts and restarts when the tab becomes visible or the network returns. There are no push notifications; the page title carries the needs-you count.
- Terminal traffic has its own allowance per device, so shells neither starve the agent calls nor are starved by them: bursts of 80 requests, then 40 per second (a held output request counts once). Opening a terminal: 3 at once, then one every 5 seconds. At most 4 shells are open at once over all devices (`409` for a fifth). One input request carries at most 4096 characters; a terminal is 10 to 400 columns and 3 to 200 rows. The server keeps the last 256 KiB of each shell's output for a client that reconnects; output older than that is not replayed, the page shows what the shell still redraws. A shell that ended stays listed for 2 minutes so a reload can show how it ended.

## Threat model

**The token is control of your agents, and with the terminal switched on, a shell.** Whoever holds it can send any prompt to any agent, answer approvals and interrupt or quit agents, and an agent that is told to run a command does. Treat it like an SSH key: it is remote code execution as your user through the agents. With the terminal off (the default) it is not a shell: the API types into agents and, for an account switch, one `cd … && omp …` line into the plain shell left after omp quit (appended to any text already typed there); it cannot close panes, and reads no file but the ones named above. With `remote.terminal` or `--terminal` on, a stolen token is a login shell as your user, with your files, keys and credentials, until you rotate it (see Terminal). `POST /api/sessions` does start a new agent, so it is one more way to run work on your accounts' quota: it accepts only the directories and accounts it listed itself (a `dir` outside `~` and `~/Projects/*` and the live agents' directories is `400`; the profile is validated as a plain name and shell-quoted) and `--read-only` refuses it.

- It sits in plaintext at mode `0600` (the server refuses a file that others can read, a symlink or a file of another owner), and in the phone's `localStorage`. A lost phone: `hivegrid-remote token --rotate` (the running server picks it up at once, no restart) and remove the device in the Tailscale admin console.
- Anyone on your tailnet can reach the port: limit it with a Tailscale ACL that allows port 443 of this machine to your phone's user or tag only.
- The chat shows conversation text, tool calls and tool output of your agents (code, file contents, command output): treat the token as read access to that. Session files are opened only below `~/.omp/` as described above, so a state file or a symlink cannot make the server read another file; `/api/accounts` returns quota numbers and usage sums only (never a credential, token, directory or the cache file's other fields).
- What the token can now also do beyond typing into agents: **quit** an idle, done or limited omp (Ctrl+D into its pane, never a kill and never closing a pane; see Quitting a session), **start omp** from a past session (`--resume` of a file the server found itself, in its own directory) or in a folder it names, and **read files that `hivegrid-send` put in the outbox** (nothing else on disk; see Files and images to the phone). It cannot name a command or a file to read or resume: those ids come from the server's own listings. The one path it does name is the folder a new session starts in, which must exist and, with symlinks resolved, lie below your home directory with no hidden component. The folder search lists folder names below your home directory (never hidden folders, symlinks or file contents), so a stolen token also shows the layout of your project folders. The history lists the titles, first messages and directories of every past session of every account: treat the token as read access to those too.
- Pane text and session text are untrusted. The server strips escape sequences, control and bidi characters and cuts lengths, and the page sets every agent-derived text with `textContent`; its content security policy forbids inline script and any other origin.
- The directory of the agents' state files (`$XDG_RUNTIME_DIR/hivegrid-agents`, else `/tmp/hivegrid-agents`) drives prompts, model switches and which session file is read, so the server refuses to start when it is not a real directory of your user that others cannot write to.
- A page on another site cannot drive the server from your phone's browser: the token is no cookie, a write needs `Content-Type: application/json` and an `X-Hivegrid-Remote` header (no CORS answer is ever sent), and the `Host` and `Origin` headers are checked (`*.ts.net`, loopback and `--allow-host` names only).
- The fonts are public system files of the machine and are served without the token (the `Host` check still applies); they reveal nothing the browser could not get from any machine with the same package. The content security policy allows fonts, images and everything else from the same origin only.
- Nothing logs a token, a header, a query string, a prompt, chat text or a path; a write logs the action and the agent's label (a new session logs the account name only; an account switch logs the agent's label, never the account, a path or the chat).
- The token itself does not expire: the real controls are rotation, `--read-only` and removing the device. Terminals expire on their own (see Terminal).
- The terminal (off unless you switch it on) logs only that one was opened or closed, with a running number and the reason; never what was typed or printed, a session id, a directory or a size. Its shells get a small environment (`PATH`, locale, session variables such as `DISPLAY` and `SSH_AUTH_SOCK`, plus `HOME`, `USER`, `LOGNAME`, `SHELL`, `TERM`): the server's own `HIVEGRID_REMOTE_*` settings and the pane variables of the window it was started from stay out of it. Each terminal belongs to the token that opened it.

Details about each defence are in the module `bin/hivegrid_remote.py`; `dev/qa/remote-smoke` exercises the server against a sandbox Hivegrid (local only, QA slot 14), and `dev/qa/remote-term-smoke` drives the terminal through the real server in a throwaway home (no window needed).
